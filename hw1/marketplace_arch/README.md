
# Архитектурное проектирование маркетплейса

В этом домашнем задании я спроектировала архитектуру маркетплейса, где продавцы размещают товары, а покупатели их заказывают.

## Описание кейса

Маркетплейс должен уметь:
- показывать покупателям персонализированную ленту товаров
- давать продавцам возможность управлять каталогом
- управлять пользователями (и покупателями, и продавцами)
- оформлять заказы
- считать и учитывать платежи
- отправлять уведомления о статусах заказов

Я добавила еще несколько вещей, которые в реальном маркетплейсе точно будут: доставку, техподдержку, поиск по каталогу

## Домены и их ответственность

Каждый домен отвечает за свою часть работы:

**Каталог товаров** - управляет карточками товаров, категориями, ценами и остатками на складе

**Поиск** - отвечает за быстрый полнотекстовый поиск и фильтрацию товаров. Работает с индексом, а не с основной базой каталога.

**Корзина** - хранит временный состав покупок пользователя до момента оформления заказа.

**Заказы** - управляет жизненным циклом заказа: создание, оплата, отмена, закрытие.

**Платежи** - проводит оплату через внешний платежный шлюз, учитывает транзакции и возвраты.

**Доставка** - рассчитывает стоимость доставки, создает заявки у внешних логистических провайдеров, отслеживает трек-номера.

**Пользователи** - хранит профили, адреса доставки, настройки уведомлений для покупателей и продавцов.

**Аутентификация** - проверяет логины и пароли, выдает JWT-токены, управляет ролями.

**Уведомления** - отправляет email, SMS и push-уведомления на основе событий из системы.

**Персонализация** - анализирует поведение пользователей и формирует персонализированную ленту рекомендаций.

**Техподдержка** - агрегирует данные о заказах и пользователях для операторов поддержки.

## Как я распределила домены по сервисам

Каждый домен стал отдельным микросервисом. 

**Каталог и Поиск разделила**, потому что у них разные требования к данным. Каталог это система учета, где важна строгая согласованность (ACID), поэтому там PostgreSQL. Поиск это система чтения, где нужна скорость по миллионам товаров, поэтому там Elasticsearch.

**Корзину выделила отдельно от Заказов**, потому что корзина меняется очень часто, а заказ должен быть стабильным. К тому же корзина хранит временные данные, поэтому там Redis, а не PostgreSQL.

**Платежи отделила от всего**, потому что они работают с чувствительными финансовыми данными. Это требует изоляции периметра безопасности и соответствия стандартам типа PCI DSS.

**Доставку вынесла отдельно**, потому что это отдельный ограниченный контекст. Для заказа важны состав и сумма, а для доставки важны габариты, вес и трек-номера. Это две разные модели данных.

**Уведомления отделила**, потому что они работают асинхронно и не должны блокировать основные процессы. Если почтовый сервер упал, маркетплейс должен продолжать принимать заказы.

**Персонализацию вынесла отдельно**, потому что это постоянно меняющаяся часть системы. ML-инженеры регулярно тестируют новые алгоритмы выдачи товаров.

**Техподдержку выделила**, потому что операторам нужен доступ к данным из разных сервисов, но давать им прямой доступ к базам данных других сервисов нельзя. Техподдержка агрегирует данные через API.

## Границы владения данными

Каждый сервис владеет своей базой данных. Никаких разделяемых БД нет. 

| Сервис | База данных | Что хранит |
|--------|-------------|------------|
| Сервис аутентификации и авторизации | БД Аутентификации (PostgreSQL) | Логины, хэши паролей, токены, роли |
| Сервис Управления пользователями | БД Пользователи (PostgreSQL) | Профили, адреса, настройки |
| Сервис каталога товаров | БД Каталога товаров (PostgreSQL) | Товары, категории, цены, остатки |
| Сервис поиска товаров | БД Поиска товаров (Elasticsearch) | Индекс для полнотекстового поиска |
| Сервис корзины | БД Корзины (Redis) | Состав корзин пользователей |
| Сервис Заказов | БД Заказов (PostgreSQL) | Заказы, состав заказов, статусы |
| Сервис платежей | БД Платежи (PostgreSQL) | Транзакции, статусы платежей |
| Сервис доставки | БД Доставки (PostgreSQL) | Заявки на доставку, трек-номера |
| Сервис уведомлений | БД Уведомлений (PostgreSQL) | Шаблоны уведомлений, история отправок |
| Сервис Персонализации | БД Персонализация (ClickHouse) | События поведения, ML-профили |
| Сервис Техподдержки | БД чата и поддержки (PostgreSQL) | Тикеты, обращения пользователей |

Только владелец сервиса может читать и писать в свою базу. Если Сервису Заказов нужны данные пользователя, он запрашивает их через API Сервиса Управления пользователями

## Взаимодействия между сервисами

Я разделила взаимодействия на два типа: синхронные и асинхронные. Синхронные вызовы только там, где нужен немедленный ответ пользователю, все остальное уходит в события.
### Синхронные вызовы

Синхронно общаются только те части системы, где человек ждет ответ на экране прямо сейчас:

- Клиенты (веб, мобильное приложение, кабинет продавца, административная панель) обращаются к API Gateway по HTTP/REST, и Gateway маршрутизирует запросы к сервисам. 
- Внутри бэкенда синхронных вызовов между сервисами всего три, все по gRPC:
  - Сервис Заказов читает состав корзины из Сервиса корзины в момент оформления заказа
  - Сервис Техподдержки читает историю заказов из Сервиса Заказов для экрана оператора
  - Сервис Техподдержки читает профиль пользователя из Сервиса Управления пользователями для экрана оператора

Все остальные данные клиентское приложение передает в Сервис Заказов через API Gateway одним запросом на создание заказа. Благодаря этому Сервис Заказов не вызывает никого синхронно, и в системе не появляется длинных цепочек вызовов, которые суммируют задержки сети и приводят к каскадным сбоям.

### Асинхронные вызовы (Kafka)

Все, что не требует немедленного ответа, уходит в брокер сообщений в виде событий. Основные события:

**Сервис каталога товаров публикует:**
- product.created, product.updated, product.deleted - изменения товаров

**Сервис Заказов публикует:**
- order.created - заказ создан
- order.paid - заказ оплачен
- order.cancelled - заказ отменен

**Сервис платежей публикует:**
- payment.succeeded - оплата прошла
- payment.failed - оплата не прошла

**Сервис доставки публикует:**
- delivery.status_changed - статус доставки изменился

**Кто читает события:**
- Сервис поиска товаров читает product.* и обновляет поисковый индекс (CQRS)
- Сервис Заказов читает payment.succeeded и delivery.status_changed
- Сервис доставки читает payment.succeeded и начинает сборку
- Сервис уведомлений читает все события и отправляет уведомления
- Сервис Персонализации читает всё для аналитики
- Сервис корзины читает order.created и очищает корзину

## Альтернативные варианты декомпозиции

Я рассматривала три варианта архитектуры.

### Вариант 1: Модульный монолит

Вся система это одно приложение, разделенное на модули внутри. Модули не могут обращаться друг к другу напрямую, только через публичные интерфейсы.

**Плюсы:**
- Проще разрабатывать на старте
- Нет сетевых задержек между модулями
- Проще тестировать (не нужно поднимать много контейнеров)
- Проще деплоить (один артефакт)
- Проще обеспечить согласованность данных (одна транзакция)

**Минусы:**
- При росте системы становится сложнее менять код
- Все модули деплоятся вместе, даже если изменился только один
- Одна ошибка может уронить всю систему
- Сложнее масштабировать отдельные части
- Команды мешают друг другу при работе над одним репозиторием

**Trade-off:** Мы получаем простоту разработки ценой потери независимости команд и масштабирования.

### Вариант 2: Микросервисы с синхронной оркестрацией 

Каждый домен это отдельный сервис. Сервис Заказов выступает оркестратором и синхронно вызывает все нужные сервисы: Сервис корзины, Сервис каталога товаров, Сервис Управления пользователями, Сервис доставки, Сервис платежей.

**Плюсы:**
- Понятная логика (Сервис Заказов управляет всем процессом)
- Проще отлаживать (видно всю цепочку в одном месте)
- Подходит для простых сценариев

**Минусы:**
- Временная связанность: если Сервис платежей упал, Сервис Заказов тоже не сможет работать
- Каскадные сбои: медленный ответ от одного сервиса блокирует все остальные
- Сервис Заказов становится объектом, который знает про всех
- Длинные цепочки вызовов суммируют задержки сети
- Сложно обеспечить отказоустойчивость

**Trade-off:** Мы получаем понятную логику ценой надежности и масштабируемости. По сути, этот вариант превращает систему в распределенный монолит.

### Вариант 3: Event-driven микросервисы (финальный выбор)

Каждый домен это отдельный сервис. Синхронные вызовы оставлены только там, где нужен немедленный ответ пользователю, все остальное уходит в события Kafka.

**Плюсы:**
- Сервисы слабо связаны 
- Высокая отказоустойчивость: упал Сервис уведомлений, заказы все равно оформляются
- Можно независимо деплоить и масштабировать каждый сервис
- Легко добавлять новые потребители событий
- Хорошо подходит для сложных бизнес-процессов

**Минусы:**
- Сложнее отлаживать (события асинхронные)
- Нет ACID между базами, нужно использовать Saga
- Eventual consistency: данные могут быть несогласованы короткое время
- Нужна зрелая инфраструктура (брокер, мониторинг, трассировка)
- Сложнее для разработчиков, которые не работали с событийной архитектурой

**Trade-off:** Мы получаем надежность и масштабируемость ценой сложности разработки и эксплуатации.

## Почему я выбрала третий вариант

Я выбрала event-driven микросервисы, потому что:

1. **Маркетплейс это высоконагруженная система.** Покупателей много, и система должна быть отказоустойчивой. Если упал сервис уведомлений, мы не должны терять заказы.

2. **Разные части системы меняются с разной скоростью.** Персонализация и поиск меняются часто, платежи и каталог должны быть стабильными. Разделение на независимые сервисы позволяет командам работать параллельно.

3. **Разные требования к масштабированию.** Разные части приложения нагружены неравномерно. Каталогу нужны десятки серверов и кэширование, чтобы выдерживать миллионы просмотров страниц. В платежах запросов меньше, но они требуют высокой надежности и защиты.

4. **Уведомления не должны блокировать заказы.** Пользователь не должен ждать, пока отправится письмо. Асинхронная обработка через Kafka решает эту проблему.

## Инструкция запуска

Для демонстрации я подняла в Docker Сервис Персонализации. Это сервис-заглушка без бизнес-логики, который просто отвечает 200 OK на health-check.

### Требования

- Docker Desktop (для Mac/Windows) или Docker Engine + Docker Compose (для Linux)

### Шаги для запуска

1. Клонируйте репозиторий:

`git clone <URL>`
`cd marketplace_arch

2. Соберите и запустите сервис:
`docker compose up --build -d`

3. Проверьте статус контейнера:
`docker compose ps`

4. Проверьте health-check endpoint
`curl -i http://localhost:8000/health`
